# Employee Identity

## Employee Code

Employee code is a stable business identifier generated by the backend. It is not the primary key; `users.id` remains the UUID primary key.

Format:

```text
HCS_<DEPARTMENT><SEQUENCE>
```

Examples:

```text
HCS_HR001
HCS_IDS001
HCS_GIS001
```

Validation regex:

```text
^HCS_[A-Z]{2,10}[0-9]{3,5}$
```

Rules:

- Employee code is unique.
- Employee code is not reused.
- Employee code is not deleted when employment ends.
- Employee code does not change during department transfer.
- Legacy technical or system admin accounts may have no employee code.
- Frontend must not submit or decide the official employee code.
- Backend must not use `MAX + 1`.

## Sequence Generation

Sequences are stored in `department_employee_sequences`.

When an employee account is created, the backend:

1. validates the department is active;
2. starts a transaction;
3. creates or updates the department sequence row with an atomic upsert;
4. increments the sequence;
5. creates `HCS_<DEPARTMENT><SEQUENCE_PADDED>`;
6. inserts the user;
7. creates the initial department history row;
8. writes audit events in the same transaction.

Technical accounts do not receive employee codes and do not increment department sequences.

## Departments

Departments are stored in `departments`.

Code rules:

- uppercase;
- 2 to 10 characters;
- only `A-Z`, `0-9`, and `_`.

The current department is stored on `users.department_id` and exposed as `departmentCode` and `departmentName` by the API.

## Department History

Department transfers are stored in `employee_department_history`.

The active row has:

```text
effective_to = null
```

Each transfer:

1. locks the user row;
2. closes the current active history row;
3. creates a new history row;
4. updates the user's current department;
5. writes audit action `employee_department_transfer`.

The unique active-history index prevents two active department rows for the same user.

## Traceability

Use:

```text
GET /api/admin/users/:id/department-history
```

The response includes old department, new department, effective dates, reason, decision number, notes, actor, and created timestamp.

## Employment End

When employment status becomes `terminated` or `retired`:

- user is not deleted;
- employee code is retained;
- employee code is not reused;
- active sessions are revoked;
- current department history is closed;
- audit action `employment_status_change` is recorded.

Employment start and end are date-only business fields:

- API accepts `YYYY-MM-DD`.
- API returns `YYYY-MM-DD`.
- UI displays `DD/MM/YYYY`.
- Database stores `employment_started_on` and `employment_ended_on` as `date`.
- `created_at`, `updated_at`, `last_login_at`, and `password_changed_at` remain timestamps.
- If start date is omitted when creating an employee, PostgreSQL `CURRENT_DATE` is used.
- End date cannot be earlier than start date.

If an employee returns, HR must decide manually whether to use the old profile or create a new one. The system must never assign an existing employee code to another person automatically.

## Audit Actions

- `employee_code_change_rejected`
- `department_create`
- `department_update`
- `department_status_change`
- `employee_department_transfer`
- `employment_status_change`
